# OpenCV 4.7.0 DNN production-source safety audit checkpoint

## Status

**Executed source audit: PASS as a real-project hazard/provenance checkpoint. R3 C3 remains PARTIAL.**

This audit inspects the exact official OpenCV 4.7.0 source revision used by the real-project runtime campaign:

`725e440d278aca07d35a5e8963ef990572b07316`

Target production source file:

`modules/dnn/src/layers/convolution_layer.cpp`

The purpose is to verify that the production DNN implementation contains concrete aliasing, side-effect, lifetime, and control-flow hazards that justify the manuscript's fail-closed displacement rules. This checkpoint does **not** claim that the released artifact automatically rewrites OpenCV source, and it does **not** close the reviewer request for real-project transformation-equivalence evidence.

## Observed production-C++ safety hazards

### 1. Pointer/reference aliasing is real, not hypothetical

The DNN convolution implementation uses smart-pointer references and raw pointer-bearing containers in production methods, including `tryFuse(Ptr<Layer>& top)` and `applyHalideScheduler(Ptr<BackendNode>& node, const std::vector<Mat*>& inputs, ...)`. More importantly, `fuseWeights` contains an explicit data-alias check:

`if (weightsMat.data == blobs[0].data) weightsMat = weightsMat.clone();`

This is direct production evidence that storage aliasing is semantically relevant. A call-use displacement that crosses such storage relationships cannot be treated as safe without resolving the alias relation.

**Fail-closed implication:** unresolved pointer/reference/data aliasing must reject a displacement candidate.

### 2. Side effects and mutable object state are pervasive

`setActivation` and fusion paths mutate persistent layer state such as `activ`, `reluslope`, `newActiv`, `activType`, CUDA fusion/activation fields, `fusedActivation`, `weightsMultipliers`, `weightsMat`, and `biasvec`. `fuseWeights` performs multiplicative/additive updates to stored weights and biases.

These are observable state transitions. Reordering a call across them can change later behavior even when the moved call itself appears independent at the syntax level.

**Fail-closed implication:** a candidate crossing unresolved writes, object-state mutations, or state-dependent calls must be rejected.

### 3. Lifetime and resource-release order matters

The production class contains explicit release/destruction behavior. Under Tengine support, `~ConvolutionLayerImpl()` releases `tengine_graph`; `finalize` can also release/reset `tengine_graph`. Under OpenCL, `finalize` releases `convolutionOp`. Local `Mat` objects and smart pointers additionally have RAII-managed lifetimes.

Moving work across a release/destructor boundary can change lifetime, resource ownership, or the order in which dependent state remains valid.

**Fail-closed implication:** unresolved destructor, resource-release, or object-lifetime boundaries must reject displacement.

### 4. Error/exception/control-flow order is semantically relevant

The same production file contains many `CV_Assert` checks and `CV_Error(...)` paths. For example, `getMemoryShapes` validates shape/group constraints and raises an error when the number of input channels is incompatible with the group configuration.

A displacement that moves a stateful or failing operation across an assertion/error path can alter which side effects occur before failure or whether an operation executes at all.

**Fail-closed implication:** unresolved exception/error-order or early-return dependencies must reject displacement.

## Relationship to the manuscript safety predicates

The exact OpenCV 4.7.0 production source therefore supplies concrete real-project examples for four hazard families already represented in the manuscript's conservative gate:

- pointer/reference aliasing;
- unordered side effects and mutable object state;
- lifetime/destructor/resource-release ordering;
- exception/error/control-flow ordering.

This strengthens the provenance of the fail-closed policy: these hazards are present in the real target codebase rather than only in synthetic negative tests.

## Evidence boundary

This audit is intentionally narrower than a completed transformation-safety experiment.

What it establishes:

- exact real-project production source was inspected;
- all four requested hazard families occur in the OpenCV DNN production implementation;
- the fail-closed safety policy is directly relevant to the selected real-world target;
- a concrete alias-protection idiom (`weightsMat.data == blobs[0].data` followed by cloning) is present in production code.

What it does **not** establish:

- no OpenCV source-to-source transformation is automatically generated by the released artifact;
- no production OpenCV call-use displacement is yet claimed safe;
- no original-versus-transformed OpenCV binary equivalence result is claimed;
- no production sanitizer/equivalence run for a transformed OpenCV source tree is claimed.

Therefore **R3 C3 remains Partial**. The next closure-grade safety step must identify a genuinely permitted production candidate (if one exists under the fail-closed gates), implement that bounded transformation explicitly, rebuild the same exact OpenCV revision, and execute matched functional/performance checks with sanitizer coverage. If no candidate passes, the scientifically valid result is to report fail-closed rejection rather than force a transformation.
